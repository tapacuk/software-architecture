### Questions

1.  Що таке Code Smells? Які ви знаєте види? Наведіть приклади. Чому це погано?

    Code Smells (запахи коду) — це певні ознаки в сирцевому коді, які вказують на глибші проблеми проектування. Вони не є помилками (код працює), але роблять систему вразливою до багів у майбутньому. Основні види включають роздувачі (Bloaters), порушники ООП, перешкоди для змін та надмірність. Прикладами є «Довгий метод», «Великий клас» або «Дубльований код». Це погано, бо такий код важко читати, тестувати та підтримувати, а будь-яка зміна може "зламати" сусідні модулі.

2.  Що таке spaghetti code? Чому це вважається поганою практикою?

    Spaghetti code — це код із заплутаною структурою, де логіка управління передається хаотично, без чіткого поділу на модулі чи класи. Назва походить від аналогії з тарілкою спагеті, де неможливо витягнути одну нитку, не зачепивши інші. Це вважається поганою практикою, бо такий код майже неможливо аналізувати та розширювати. Виправлення однієї помилки в "спагеті" часто призводить до появи трьох нових у непередбачуваних місцях через приховані зв'язки.

3.  Які Code Smells належать до недоліків рівня застосування? Чому?

    На рівні застосування виділяють такі запахи, як Contrived Complexity (надумана складність) та Shotgun Surgery (стрільба дробом). Останній виникає, коли для внесення однієї невеликої зміни вам доводиться редагувати десятки різних класів по всьому проекту. Ці недоліки стосуються архітектури в цілому, оскільки вони свідчать про неправильний розподіл обов'язків між компонентами системи. Вони роблять проект занадто жорстким і неповоротким для масштабування.

4.  Які Code Smells належать до недоліків рівня класів? Чому?

    До них належать Large Class (Божественний клас), Lazy Class (Ледачий клас) та Data Class (Клас-контейнер даних без логіки). "Великий клас" намагається виконувати занадто багато роботи, що порушує принцип єдиної відповідальності (SRP). Навпаки, "Ледачий клас" майже нічого не робить і лише даремно ускладнює структуру. Ці запахи виникають через неправильне моделювання предметної області, що призводить до низької згуртованості коду всередині класів.

5.  Які Code Smells належать до недоліків рівня методів? Чому?

    Це найпоширеніші запахи: Long Method (Задовгий метод), Long Parameter List (Забагато параметрів) та Feature Envy (Заздрість до чужих даних). Задовгий метод важко осягнути розумом, а велика кількість аргументів робить виклик функції нечитабельним. "Заздрість до даних" проявляється, коли метод більше цікавиться даними іншого об'єкта, ніж власного класу. Це ознака того, що логіку розмито і її потрібно декомпозувати або перенести в інше місце.

6.  Для чого потрібні шаблони проектування? Які задачі/ проблеми вони допомагають вирішити?

    Шаблони проектування (Design Patterns) — це перевірені часом типові рішення стандартних проблем, що виникають при проектуванні ПЗ. Вони допомагають уникнути "винаходу велосипеда" та забезпечують спільну термінологію для розробників. Шаблони вирішують завдання гнучкого створення об'єктів, ефективної побудови зв'язків між ними та зручного управління поведінкою системи. Використання патернів робить код більш читабельним, передбачуваним та легким для рефакторингу.

7.  Чи завжди потрібно використовувати багато шаблонів проектування? Чому?

    Ні, надмірне використання патернів є антипатерном, який називають Overengineering. Кожен шаблон додає проекту певний рівень абстракції, що може ускладнити розуміння коду, якщо проблема насправді проста. Слід дотримуватися принципу KISS (Keep It Simple, Stupid) — використовувати патерн тільки тоді, коли без нього код стає заплутаним або важким для розширення. Найкращий дизайн — це найпростіший дизайн, який виконує поставлені завдання.

8.  Які існують групи шаблонів проектування? Чому вони розділяються саме так?

    Патерни зазвичай ділять на три основні групи: Твірні (Creational), Структурні (Structural) та Поведінкові (Behavioral). Такий поділ ґрунтується на тому, який саме аспект системи вони "лікують". Твірні відповідають за механізм створення об'єктів, структурні — за те, як класи та об'єкти збираються у більші структури, а поведінкові — за комунікацію та розподіл обов'язків між ними. Це допомагає розробнику швидше знайти потрібний інструмент під конкретну проблему.

9.  Що таке Creational шаблони? Для чого вони потрібні і як можуть бути використані?

    Твірні шаблони (Creational patterns) фокусуються на процесі створення об'єктів, роблячи систему незалежною від того, як саме ці об'єкти створюються. Вони потрібні для того, щоб приховати складну логіку ініціалізації або контролювати кількість екземплярів класу. Наприклад, Singleton гарантує існування лише одного екземпляра, а Factory Method дозволяє створювати об'єкти, не вказуючи їхній точний клас у коді. Вони використовуються, коли пряме створення об'єкта через new робить код занадто жорстким.

10. Що таке Structural шаблони? Для чого вони потрібні і як можуть бути використані?

    Структурні шаблони (Structural patterns) визначають способи формування великих об'єктних структур із дрібних елементів. Вони допомагають забезпечити сумісність інтерфейсів та спростити взаємодію між різними частинами системи. Наприклад, Adapter дозволяє об'єктам з несумісними інтерфейсами працювати разом, а Facade створює просте "обличчя" для складної бібліотеки. Вони використовуються для мінімізації залежностей та побудови гнучких зв'язків між незалежними модулями.

11. Що таке Behavioral шаблони? Для чого вони потрібні і як можуть бути використані?

    Поведінкові шаблони (Behavioral patterns) відповідають за ефективну комунікацію між об'єктами та розподіл обов'язків. Вони потрібні для того, щоб зменшити пов'язаність (coupling) між компонентами, дозволяючи їм взаємодіяти без знання внутрішньої структури один одного. Наприклад, Observer дозволяє одним об'єктам підписуватися на події інших, а Strategy дає змогу змінювати алгоритм прямо під час виконання програми. Вони використовуються для реалізації складної логіки взаємодії, яку важко описати простою послідовністю викликів.

12. Про що говорить GRASP?

    GRASP (General Responsibility Assignment Software Patterns) — це набір із дев’яти принципів, які допомагають правильно розподілити відповідальність між класами в об'єктно-орієнтованому проектуванні. Він не про конкретні патерни, а про базову логіку: хто має створювати об'єкт, хто має володіти даними, а хто — керувати логікою. Основні принципи включають Information Expert, Creator, Low Coupling та High Cohesion. Використання GRASP робить архітектуру зрозумілою та легкою для підтримки, запобігаючи перетворенню коду на хаос.

13. Чим відрізняються централізовані репозиторії (Subversion) від розподілених (Git)?

    У централізованих системах (SVN) існує єдиний сервер, де зберігається вся історія версій, а розробник завантажує лише робочу копію файлів. Якщо сервер недоступний, ви не можете переглянути історію або зробити коміт. У розподілених системах (Git) кожен розробник має у себе на комп'ютері повну копію всього репозиторію з усією історією. Це дозволяє працювати офлайн, робити коміти локально та набагато швидше перемикатися між гілками, оскільки всі дані вже є на диску.

14. Яка структура Git репозиторію?

    Репозиторій Git складається з трьох основних частин: Working Directory (Робоча директорія), Staging Area (Індекс) та .git directory (Сховище). Робоча директорія — це файли, які ви бачите і редагуєте прямо зараз. Staging Area — це черга, куди ви додаєте зміни перед тим, як зберегти їх. Власне сховище у папці .git містить усі стиснуті об'єкти (коміти, дерева, файли) та службову інформацію про гілки та конфігурацію.

15. Які види вказівників існують в Git? В чому різниця між ними?

    Основними вказівниками є HEAD, Гілки (Branches) та Теги (Tags). HEAD — це вказівник на ваш поточний стан (зазвичай на останній коміт поточної гілки). Гілка — це рухомий вказівник на останній коміт у певній лінії розробки, який автоматично переміщується вперед при кожному новому коміті. Тег — це статичний вказівник на конкретний "важливий" коміт (наприклад, версія v1.0), який не змінюється з часом.

16. Що таке коміт? Яка його структура? Як зробити коміт?

    Коміт — це знімок (snapshot) стану вашого проекту в певний момент часу. Його структура включає унікальний SHA-1 хеш, посилання на дерево файлів, дані про автора, дату та посилання на попередній (батьківський) коміт. Щоб зробити коміт, спочатку потрібно додати зміни до індексу командою git add ., а потім виконати команду git commit -m "опис змін". Кожен коміт створює нову точку в історії, до якої можна повернутися в майбутньому.

17. В яких статусах може перебувати файл репозиторія?

    Файл у Git може перебувати в одному з чотирьох основних статусів: Untracked (новий файл, про який Git ще не знає), Unmodified (файл у репозиторії, який не змінювався), Modified (файл змінено, але зміни не додано в індекс) та Staged (зміни підготовлені до коміту). Коли ви редагуєте файл, він стає Modified. Після команди add він переходить у Staged, а після commit знову повертається до статусу Unmodified.

18. Які стани репозиторію існують і як вони пов’язані між собою?

    Репозиторій проходить через цикли взаємодії між трьома зонами: Working Directory, Staging Area та Commit History. Зміни переносяться з робочої папки до індексу (Staging) через git add, а з індексу в історію — через git commit. Також існує зворотний зв'язок: за допомогою git checkout або git restore можна витягнути файли з історії назад у робочу область. Ці стани дозволяють розробнику гнучко обирати, які саме зміни мають потрапити в наступне збереження.

19. Як можна переміщувати різні вказівники Git? Для яких цілей?

    Вказівники переміщуються командами git checkout, git switch, git reset та git merge. Наприклад, git checkout <branch> переміщує HEAD на іншу гілку, щоб ви могли працювати над іншою фічею. Команда git reset дозволяє примусово переставити вказівник поточної гілки на попередній коміт, щоб скасувати зміни. Це потрібно для навігації по історії, виправлення помилок або об'єднання різних ліній розробки.

20. Як зв’язати локальний репозиторій з віддаленим і здійснювати синхронізацію?

    Для зв'язку використовується команда git remote add origin, де origin — стандартне ім'я для віддаленого сервера. Синхронізація відбувається через три основні дії: push, fetch та pull. Команда git push відправляє ваші локальні коміти на сервер, а git fetch завантажує нові зміни з сервера, не вносячи їх у ваш код. git pull — це комбінація fetch та merge, яка завантажує зміни та одразу об'єднує їх з вашою поточною гілкою.

21. Які архітектурні шаблони та стилі ви знаєте? Як вони розділені по категоріях?

    Архітектурні стилі зазвичай поділяють за принципом організації зв'язків. Виділяють структурні стилі (багаторівнева, компонентна архітектура), стилі обміну повідомленнями (шина повідомлень, публікація-підписка), розподілені стилі (клієнт-сервер, SOA, мікросервіси) та стилі на основі даних (репозиторій, класна дошка). Також існують шаблони проектування інтерфейсу, такі як MVC, MVP або MVVM. Кожна категорія вирішує свою задачу: від масштабованості системи до зручності розділення фронтенду та бекенду.

22. В чому полягає поєднання архітектурних стилів?

    Сучасні складні системи рідко будуються на основі лише одного стилю; зазвичай вони є гібридними. Наприклад, система може бути клієнт-серверною за своєю природою, але всередині сервера використовувати багаторівневу архітектуру для логіки та шину повідомлень для зв'язку з іншими сервісами. Це дозволяє використовувати сильні сторони кожного підходу там, де вони найбільш доречні. Головне при поєднанні — чітко визначити межі (bounded contexts), щоб різні стилі не конфліктували та не ускладнювали підтримку.

23. Архітектура клієнт-сервер.

    Це модель взаємодії, де завдання розподіляються між постачальником ресурсів (сервером) і замовником послуг (клієнтом). Клієнт ініціює запити, а сервер обробляє їх, керує даними та надсилає відповідь. Це дозволяє централізовано зберігати інформацію та забезпечувати безпеку на боці сервера, тоді як клієнт фокусується на відображенні інтерфейсу користувачу. Прикладом є звичайний веб-браузер, який запитує сторінку у веб-сервера через протокол HTTP.

24. Компонентна архітектура.

    Цей стиль розглядає систему як набір незалежних, слабко пов'язаних модулів — компонентів. Кожен компонент має чітко визначений інтерфейс, через який він взаємодіє з іншими частинами системи, приховуючи свою внутрішню реалізацію. Це дозволяє замінювати або оновлювати окремі блоки без переписування всієї програми. Такий підхід дуже популярний у фронтенд-фреймворках (як-от Vue чи React) та при розробці складних корпоративних систем, де важлива перевикористовуваність коду.

25. Багаторівнева архітектура та N-рівнева архітектура.

    Багаторівнева архітектура (Layered Architecture) організовує код у горизонтальні шари, де кожен шар має свою відповідальність (наприклад: рівень представлення, бізнес-логіка, доступ до даних). N-рівнева архітектура (N-tier) — це фізичне рознесення цих шарів на різні машини в мережі (наприклад, окремі сервери для бази даних, API та клієнта). Основна перевага тут — ізоляція: зміни в базі даних не повинні напряму впливати на код інтерфейсу. Це спрощує тестування та дозволяє масштабувати окремі рівні незалежно від інших.

26. Шина повідомлень.

    Шина повідомлень (Message Bus) — це архітектурна модель, де різні компоненти системи спілкуються між собою, відправляючи повідомлення у спільний канал. Замість того, щоб звертатися один до одного напряму, модулі "підписуються" на цікаві їм типи повідомлень або "публікують" свої. Це забезпечує максимальну розв'язаність (decoupling): відправник не знає, хто отримає його повідомлення і скільки буде отримувачів. Це ідеально підходить для великих систем, де потрібно обробляти події в реальному часі від багатьох джерел.

27. Об’єктно-орієнтована архітектура.

    У цьому стилі система проектується як сукупність об'єктів, що взаємодіють між собою через виклики методів. Архітектура базується на принципах інкапсуляції, успадкування та поліморфізму, де дані та поведінка об'єднані всередині сутностей. Основна мета — відобразити реальні об'єкти предметної області в коді, що робить структуру програми більш інтуїтивною для розробника. Проте при неправильному проектуванні вона може призвести до надмірної пов'язаності об'єктів, що ускладнює зміни.

28. Сервісно-орієнтована архітектура.

    SOA (Service-Oriented Architecture) — це стиль проектування, де функціональність системи розділена на окремі автономні сервіси, що доступні через мережу. Кожен сервіс вирішує конкретну бізнес-задачу (наприклад, "обробка платежу" або "реєстрація користувача") і спілкується з іншими через стандартні протоколи. На відміну від моноліту, SOA дозволяє різним командам розробляти сервіси на різних мовах програмування. Це забезпечує гнучкість бізнес-процесів, оскільки сервіси можна комбінувати для створення нових додатків.

29. Що варто реалізовувати, як наскрізну функціональність? Чому?

    Наскрізна функціональність (Cross-cutting concerns) — це аспекти програми, які пронизують багато модулів, але не є частиною основної бізнес-логіки. До них належать логування (logging), безпека та авторизація, обробка помилок, кешування та моніторинг. Їх варто виносити окремо (наприклад, через аспектно-орієнтоване програмування або middleware), щоб не дублювати один і той самий код у кожному методі. Це дозволяє тримати чистим основний код і централізовано керувати системними функціями.
